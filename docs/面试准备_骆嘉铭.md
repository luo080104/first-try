## 二、专长深挖问答（面试官必问——逐条准备）

### A. Go购 项目（最大专长——必被深挖）

**Q1. 介绍一下你的 Go购 项目？**
> 一句话：全网购物比价 Agent——输入商品名，四平台（淘宝/京东/拼多多/唯品会）实时比价，AI 导购建议，降价盯盘推送。它解决"想买的东西哪里最便宜"的问题。
> 架构：双通道搜索（联盟 API 快通道秒级 + 浏览器爬虫慢通道 10-30 秒全量）→ SKU 归一化 → 好价卡六维评分 → AI 导购对话 → 降价推送。

**Q2. 为什么做双通道？直接爬虫不行吗？**
> 因为"非佣金商品搜不到"——联盟 API 只覆盖有佣金的商品，很多想买的东西搜不到。所以加了浏览器爬虫通道做全量兜底。快通道保证体验，慢通道保证覆盖——这是用空间换覆盖率的工程取舍。

**Q3. 跨平台 SKU 归一化是怎么做的？**
> 四个平台的商品命名差异很大——同款商品标题不同、参数表述不同。我做的是分层匹配：先品牌+型号硬匹配，再参数特征（容量/尺寸/颜色）软匹配，最后用相似度兜底。核心是建立统一的商品身份模型，而不是靠字符串完全相等。

**Q4. 浏览器爬虫最难的点是什么？怎么解决的？**
> 验证码和登录态。弹窗调试了 9 轮——试过 headless、隐藏窗口、定时重开，最后用**浏览器常驻池 + 登录态复用**根治：保持一组常驻浏览器实例，预热四个平台的登录会话，用完不退出、复用 tab。另外还踩过 headless 破坏 CDP 导致 404、--window-position 对 Edge 无效这类坑。

**Q5. 遇到过的系统级问题举例？**
> 三个典型的：①GBK 编码——终端输出乱码不是数据损坏，重定向绕过；②进程残留——爬虫服务双残留进程每 10 分钟弹一次浏览器，排查所有进程和端口；③端口锁死——socket 占位端口冲突。这些问题的共同点是：**不能靠打补丁，要从底层找根因**——比如端口问题就要看是谁占的、为什么占。

**Q6. DeepSeek 大模型怎么接的？有哪些工程细节？**
> 接入 chat completions API 做意图解析和导购推荐。工程细节：①上下文管理——历史对话带前缀缓存（system prompt 稳定、动态内容放 user 消息），命中率从 55% 提到 94%，省了一半 token；②偶发空返回要重试；③不用 response_format 强制 JSON（不稳定）。

**Q7. 项目里 AI 辅助编程占了多少？你怎么看？**
> 我的项目全程是两个 AI 编程 Agent 协作完成的——一个负责架构设计和代码审查，一个负责编码测试——这一点我如实说明。两个月的实践让我清楚工具的强与弱：AI 生成代码快，但**不懂业务、不会替我理解底层原理**——爬虫 9 轮调试、GBK 编码、进程残留这些最后靠的还是我自己对操作系统和网络的理解。我的态度是"善于用器，更要懂器背后的逻辑"——这也是我入学后要系统补数学和计算机基础的原因。

**Q8. 好价卡六关评估是什么？**
> 价格、店铺信誉、优惠券、运费、售后、历史价格六个维度的综合评分——不只是比价格数字，而是比"实际到手成本+风险"。

**Q9. 230 次提交说明什么？**
> 说明这是一个真实项目而不是 demo——有需求变更、有 bug 修复、有重构。完整生命周期：需求→架构→开发→测试→上线→迭代。这也让我理解了一个道理：**真实项目的复杂度不在代码，在系统间的相互作用**。

**Q10. Go购 哪里做得不好？如果重来会怎么改？**
> ①一开始没想全采集通道——验证码问题如果设计阶段就考虑浏览器池会少走弯路；②模块化不够——后期加功能时耦合变高；③测试覆盖不足——很多是手动验证。重来会：先设计通道架构、模块化从第一天、核心逻辑写单测。

### B. 雕龙项目（方案设计——可能问"只设计不实现"）

**Q11. 雕龙是什么？**
> 面向中文网文作者的多 Agent 创作副驾驶——学习指定作家风格，生成"像那个人写的"章节。我负责方案设计：调研 30+ 开源项目，提炼 9 模块架构，完成 16 条设计决策并标注来源理由。

**Q12. 9 模块架构是什么？为什么这样分？**
> 市场分析师（选题）→ 架构师（大纲）→ 写手池（并行生成候选章节）→ 风格引擎（对齐风格指纹）→ 量化质检（质量把关）→ 追踪审查（伏笔一致性）。这样分是为了**把创作这个大任务拆成可独立优化的小任务**——写手池并行是关键，多 Agent 的价值就在这。

**Q13. "风格指纹"是什么？**
> 从作家作品里提取句长分布、词汇偏好、节奏特征，生成一份结构化的风格规范文件——让风格成为可量化的约束而不是玄学。这个概念的来源是：风格模仿最难的不是内容，是"像"——把"像"变成可计算的指标。

**Q14. 为什么只做方案不做实现？**
> 因为暑假时间有限，Go购 已经占用了主要精力。但方案设计本身是完整的训练：从需求拆解到模块划分到决策取舍——每条决策我都能说出"为什么这样选、来源是什么、放弃什么"。这也让我体会到：**设计能力和编码能力是两种技能，设计先行是对的**。

## 三、技术速查卡（面试可能被现场考的基础）

| 主题 | 要点（一句话） |
| --- | --- |
| Python 可变默认参数 | 默认参数在定义时绑定——不要用可变对象做默认值 |
| Git 常用命令 | add/commit/push/pull/branch/merge/rebase（cherry-pick 知道概念） |

| SQL 基础 | SELECT/JOIN/索引——SQLite 事务 |
| 大模型 API | temperature/上下文窗口/token 计费/前缀缓存/重试 |
| 时间复杂度的直觉 | 循环嵌套=乘、二分=log、排序=nlogn |
| 微积分最小必备 | 导数=变化率/梯度=多变量导数/积分=面积/链式法则（反向传播核心） |
| 线性代数最小必备 | 向量/矩阵乘法=变换/特征值（PCA 用）——概念层面 |
| 概率最小必备 | 条件概率/贝叶斯/期望/方差——RL 里到处都是 |

### 新增可能问题（基于团队情报）

**Q31. 你知道 MetaBBO 是什么吗？**
> 我在团队主页看过：Meta Black-Box Optimization——用强化学习或大模型来设计黑盒优化算法本身，而不是手工设计算法。传统的遗传算法、PSO 这些是人在调，MetaBBO 是让算法学会设计算法，减轻人工劳动。我看简历前特意查了你们的工作——无人农场和 AI 芯片都依赖底层优化算法，MetaBBO 是让算法适应真实问题而不是反过来。

**Q32. 为什么选无人农场方向，不选 AI 芯片？**
> 两个方向我都了解过。选农场有三个原因：第一，无人机路径规划+强化学习+UE 仿真，这个组合里每一步我都能想象出自己在做什么，有画面感；第二，算法要从仿真走向真实农田，这个"落地"的过程我觉得是最难也最有价值的；第三，AI 芯片优化跟长鑫合作，方向也很好，但芯片领域的领域知识（存储/时序/工艺）我完全空白，进入成本更高。农场方向我的工程能力能直接派上用场。当然如果团队需要，芯片方向我也愿意学。

**Q33. 你看过我们主页/论文吗？记得哪些？**
> 看过主页。团队做 MetaBBO 方向，核心是让优化算法具备自适应能力，学生 leader 是马泽原师兄（读博中）。主页上有 Publications 和 Repositories 板块，具体的论文我还没来得及细读——但如果需要，面试前我会把最近的 2-3 篇读完，带着问题来聊。（注：**面试前必做**——把主页 Publications 列表读一遍，至少能说出 1-2 篇论文标题和大致思路）
