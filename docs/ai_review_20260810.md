### [🔴 CRITICAL] SQL Injection via f-string in query_items
- **Line:** db.py lines 236-244 (query_items function)
- **Problem:** The `order` variable is built from user input via `sort` parameter and inserted directly into SQL using f-string: `ORDER BY {order}`. While the current code uses a whitelist dict lookup, the `wsql` string is also built via f-string concatenation with user-controlled `where` clauses. If the `sort` parameter ever receives an unexpected value, it falls back to 'price ASC', but the pattern of f-string SQL construction is dangerous and fragile. More critically, the `where` clauses use parameterized queries correctly, but the `order` f-string pattern could be exploited if the dict lookup is ever modified.
- **Fix:** Use a whitelist approach with explicit mapping and never interpolate user input directly into SQL. For the ORDER BY clause, use a mapping dict and validate the input strictly:
```python
order_map = {'price_asc': 'price ASC', 'price_desc': 'price DESC', 'sales': 'sales DESC', 'newest': 'first_seen DESC'}
order = order_map.get(sort, 'price ASC')
# Then use f-string only with the validated value
```

### [🟠 HIGH] Unhandled Exception in search_bili_api
- **Line:** app.py lines 100-140
- **Problem:** The `search_bili_api` function has no try/except wrapper. If `subprocess.Popen` fails (e.g., Edge not found), or `read_content_items` raises an exception, the endpoint will return a 500 error. Also, the `edge` variable could be `None` if neither Edge path exists, causing `subprocess.Popen(None, ...)` to crash.
- **Fix:** Add proper error handling:
```python
if not edge:
    return {'error': 'Edge browser not found'}
try:
    subprocess.Popen([...])
except Exception as e:
    return {'error': f'Failed to launch Edge: {str(e)}'}
```

### [🟠 HIGH] Race Condition in Crawl Task Management
- **Line:** app.py lines 510-520 (api_crawl), db.py lines 380-420 (mark_crawl_task)
- **Problem:** The `api_crawl` endpoint checks `get_progress().get('running')` before starting a new crawl, but this check-then-act pattern is not atomic. Two concurrent requests could both pass the check and start crawl tasks simultaneously.
- **Fix:** Use a threading.Lock or asyncio.Lock to make the check-and-start atomic:
```python
crawl_lock = asyncio.Lock()
@app.post('/api/crawl')
async def api_crawl(...):
    async with crawl_lock:
        if get_progress().get('running'):
            return {'ok': False, 'msg': '采集已在运行中'}
        # start crawl
```

### [🟠 HIGH] Blocking Calls in Async Endpoints
- **Line:** app.py lines 510-520 (api_crawl), lines 455-470 (api_invite_gen)
- **Problem:** `api_crawl` calls `asyncio.create_task(run_crawl_round(...))` which is fine, but `api_invite_gen` and other endpoints perform synchronous database operations directly in async functions without `asyncio.to_thread`. This blocks the event loop.
- **Fix:** Wrap synchronous DB operations in `asyncio.to_thread()` or make the endpoints synchronous (remove `async` keyword).

### [🟠 HIGH] Potential Memory Leak in SSE Generator
- **Line:** app.py lines 180-350 (search_sse)
- **Problem:** The SSE generator function `gen()` accumulates all items in memory (`all_items`, `groups`, etc.) before sending the final response. For large searches, this could consume significant memory. Also, if the client disconnects, the generator continues running until it completes.
- **Fix:** Add disconnect detection using `request.is_disconnected()` and yield periodically. Also consider streaming results incrementally rather than accumulating everything.
